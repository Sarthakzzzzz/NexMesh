# NexMesh

NexMesh is a decentralized federated-learning network where multiple independent machines collaboratively train a neural network while keeping their raw training data local.

## Architecture

```text
                    NexMesh Coordinator
                           │
                 ┌─────────┴─────────┐
                 │                   │
            Node Registry       FL Job Manager
                 │                   │
          ┌──────┼──────┬────────────┘
          │      │      │
          ▼      ▼      ▼
       Node 1  Node 2  Node 3  ... Node N
          │      │      │
       Data 1  Data 2  Data 3  ... Data N
          │      │      │
          └──────┼──────┘
                 │
           Local Training
              (PyTorch)
                 │
           Model Updates
          (No raw data)
                 │
                 ▼
        Federated Aggregation
              (FedAvg)
                 │
                 ▼
            Global Model
                 │
          ┌──────┼──────┬──────┐
          ▼      ▼      ▼      ▼
       Node 1  Node 2  Node 3  ...
```

## How It Works

1. Each node keeps its training dataset locally.
2. The coordinator distributes the current global model to participating nodes.
3. Each node trains the neural network locally using its private data.
4. Nodes send model updates to the federation; raw training data stays on the node.
5. NVFlare aggregates the updates using FedAvg to produce a new global model.
6. The updated global model is distributed back to the nodes for the next round.

## Current Implementation

- NVIDIA FLARE is used for federated-learning orchestration and model exchange.
- PyTorch is used for the MNIST neural network and local training.
- Three client datasets are generated by a seeded split, with 20,000 samples per client.
- Client datasets have no pairwise image overlap.
- FedAvg is configured for three clients and five rounds.
- Client pods can train with CUDA on an NVIDIA GeForce RTX 5050.
- Kubernetes deploys the NVFlare server and client nodes as containers.
- Raw client datasets are mounted only at their corresponding client pods.
- A separate server test split is available for global evaluation.

## Main Files

- `jobs/fedavg_nn/job.py` - NVFlare FedAvg job definition.
- `jobs/fedavg_nn/train.py` - client-side PyTorch training.
- `jobs/fedavg_nn/server_evaluator.py` - server evaluation component.
- `workspace/fedlearn/split_mnist.py` - deterministic dataset generation.
- `kind-config.yaml` - local Kind node and mount template.
- `k8s/` - Kubernetes deployment manifests.
- `commands.md` - setup, deployment, verification, and cleanup commands.

## Current Limitation

The current implementation uses a fixed local NVFlare federation with three client sites. Dynamic autonomous node registration and automatic node admission are planned as the next architectural layer.
